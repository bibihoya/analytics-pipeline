# Online Cinema Analytics

Реализованы два сервиса на Go: `movie-service` принимает и генерирует события, `aggregation-service` рассчитывает метрики и экспортирует их в S3. Один Go-модуль, отдельные программы и контейнеры.

```text
Movie Service → Kafka → ClickHouse Kafka Engine → Materialized View → raw_events
                                                                        ↓
                                                               Aggregation Service
                                                                 ↓            ↓
                                                      ClickHouse aggregates  PostgreSQL
                                                                 ↓            ↓
                                                              Grafana       MinIO
```

## Запуск

Нужен Docker с Compose. Все зависимости и сервисы собираются автоматически:

```powershell
docker compose up --build -d
docker compose ps
```

`.env` необязателен: рабочие значения заданы в Compose. Для изменения настроек можно скопировать `.env.example` в `.env`. Первый запуск скачивает образы и Go-зависимости; MinIO собирается из исходников официального релиза, зафиксированного в `deploy/minio/Dockerfile`, поскольку опубликованные образы этого релиза недоступны в официальных registry.

Kafka поднимается из трёх узлов KRaft с совмещёнными ролями broker/controller. Топик создаётся автоматически: 3 партиции, replication factor 3, min ISR 2. SQL из `migrations/` автоматически выполняется при инициализации БД. Продюсер регистрирует Avro-схему в Schema Registry; сервис агрегации создаёт бакет. Datasource, плагин и дашборд Grafana подготовлены автоматически.

| Компонент | Адрес | Доступ по умолчанию |
| --- | --- | --- |
| Movie Service | http://localhost:18080 | `POST /events`, `GET /health` |
| Aggregation Service | http://localhost:18081 | `POST /aggregate?date=YYYY-MM-DD`, `POST /export?date=YYYY-MM-DD`, `GET /health` |
| ClickHouse HTTP | http://localhost:18123 | `default` / `cinema`, БД `cinema` |
| PostgreSQL | localhost:15432 | `cinema` / `cinema`, БД `cinema` |
| Schema Registry | http://localhost:18085 | subject `movie-events-value` |
| Grafana | http://localhost:13000/d/cinema-analytics | `admin` / `admin` |
| MinIO S3 | http://localhost:19000 | `minioadmin` / `minioadmin` |
| MinIO Console | http://localhost:19001 | `minioadmin` / `minioadmin` |

Генератор сначала публикует историю за восемь завершённых дней, затем создаёт текущие сессии. Последовательность: поиск → начало просмотра → пауза → продолжение → завершение → лайк; часть пользователей прекращает просмотр после паузы. В рамках сессии сохраняются пользователь, фильм и устройство, прогресс не уменьшается. Время и прогресс исторических событий согласованы; текущие сессии ускорены для демонстрации. После повторного запуска продюсера история генерируется заново как новые сессии.

Расчёт запускается сразу при старте агрегации, затем раз в `AGGREGATION_INTERVAL` (по умолчанию `1m`). Пересчитываются сегодня и восемь предыдущих дней: так обновляются D1–D7 старых когорт. После успешного пересчёта завершённого дня его агрегаты экспортируются в MinIO. Во время наполнения первая версия метрик может быть неполной; следующий цикл обновит её.

## Схема и хранение

Схема: `schemas/movie-event-v1.avsc`. UUID представлен Avro `string` с logical type `uuid`, время — `timestamp-millis`, типы события и устройства — enum. `movie_id` может быть пустым у `SEARCHED`, `progress_seconds` по умолчанию 0. HTTP API требует корректный `event_id`, пользователя, сессию, время, типы и неотрицательный прогресс. Принимает JSON, проверяет поля и кодирует событие по Avro-схеме до отправки. В Kafka передаётся Confluent wire format со schema ID. Schema Registry назначает версии; политика совместимости — `BACKWARD_TRANSITIVE`, повторная регистрация той же схемы идемпотентна.

Ключ партиционирования — `user_id`: все действия пользователя попадают в одну партицию. Продюсер использует `acks=all`, идемпотентность Kafka-клиента и последовательные запросы к брокеру. Retry с exponential backoff сохраняет порядок; ошибка публикации возвращает HTTP 503. Успешный ответ HTTP 201 содержит `event_id`.

`cinema.kafka_events` читает Avro через Kafka Engine и Schema Registry. Materialized View переносит события в `cinema.raw_events` на `ReplacingMergeTree`. Партиции — по месяцу, сортировка — день, пользователь, `event_id`: это подходит дневным метрикам и когортам. Повторная доставка одного события с теми же полями устраняется по ключу; запросы агрегации используют `FINAL`, не ожидая фонового слияния. Это обработка at-least-once доставки; повторный запрос должен сохранять исходные `event_id` и остальные поля.

Расчёты выполняются SQL-запросами ClickHouse с `uniqExactState`/`uniqExactMerge`, `sumIf`, `countIf`, `min` и `groupUniqArray`. Дневные счётчики, среднее и топ фильмов вычисляются одним запросом по общему набору событий; показатели когорт — отдельным запросом:

| Метрика | Определение |
| --- | --- |
| `dau` | Уникальные пользователи с любым событием за UTC-день |
| `average_watch_seconds` | Средний `progress_seconds` у `VIEW_FINISHED` |
| `top_movies` | До 10 фильмов по числу `VIEW_STARTED`; при равенстве — по `movie_id` |
| `view_conversion` | Число `VIEW_FINISHED` / число `VIEW_STARTED` за день |
| `retention_d1`, `retention_d7` | Доля пользователей когорты первого `VIEW_STARTED`, имеющих любое событие ровно через 1/7 UTC-дней |
| `cohort_retention`, измерение `0`–`7` | Доля пользователей когорты первой активности, имеющих любое событие в соответствующий день жизни |
| `cohort_size` | Размер когорты; измерение `first_view` или `first_activity` |
| `views_started`, `views_finished` | Количество начал и завершений просмотра |

Для метрик retention поле `date` — дата когорты. Доли хранятся в диапазоне 0–1; Grafana отображает проценты. Будущие дни жизни и отношения с нулевым знаменателем имеют `NULL`; отсутствие завершённых просмотров даёт `NULL` среднего времени. Конверсия считается по событиям за день, поэтому при просмотрах через полночь может превышать 100%.

Результаты материализованы в ClickHouse в `aggregate_values`. После полной записи снимка сервис отмечает его в `aggregate_runs`; представление `daily_metrics` показывает последний законченный снимок за дату. Grafana читает это представление, включая cohort heatmap и графики DAU/конверсии. Raw-события в запросах дашборда не используются.

В PostgreSQL `daily_metrics` содержит дату, название метрики, измерение, значение и время расчёта. Транзакция выполняет UPSERT по `(date, metric, dimension)` и удаляет строки старого расчёта, отсутствующие в новом. Повторный расчёт обновляет значения и топ фильмов. Запись повторяется до пяти раз с backoff; при неуспехе следующий плановый цикл пробует снова. Пересчёты и экспорт внутри одного экземпляра сервиса выполняются последовательно; параллельный ручной запрос получает HTTP 409.

Экспорт читает только PostgreSQL. JSON содержит дату и все метрики с измерениями, значениями и `computed_at`. Путь: `s3://movie-analytics/daily/YYYY-MM-DD/aggregates.json`. Повторный экспорт перезаписывает объект. Ошибки чтения и загрузки логируются, выполняются повторные попытки; плановый запуск повторит неуспешную операцию. ClickHouse и PostgreSQL обновляются последовательно, без распределённой транзакции: после сбоя записи следующий пересчёт синхронизирует результаты.

## Интеграционный тест

Одна команда, в том числе на ещё не запущенном стенде:

```powershell
docker compose --profile test run --build --rm integration-test
```

Тест отправляет событие через HTTP продюсера, проверяет возвращённый ID и ожидает запись в ClickHouse до 60 секунд. Сверяет все восемь полей, включая время с точностью до миллисекунд. Каждый запуск использует новый UUID и пользователя, поэтому очистка общей БД не нужна. Других автоматических тестов нет. При локальном `go test ./...` этот тест пропускается, если не заданы `TEST_PRODUCER_URL` и `TEST_CLICKHOUSE_URL`.

## Логи и остановка

```powershell
docker compose logs --tail 50 movie-service aggregation-service
docker compose logs --tail 50 clickhouse kafka-1 schema-registry
docker compose down
```

Go-сервисы пишут JSON-логи через `slog`: `event_id`, тип и время публикации; начало/завершение расчёта, число обработанных raw-событий и длительность; ошибки, retry и результат экспорта. Именованные тома сохраняют данные после остановки.
